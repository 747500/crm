# Архитектура CRM (event/data-driven)

> Портфолио-документ. Фиксирует «дух проекта» и целевую архитектуру.
> Текущее состояние и этапы — см. `../ROADMAP.md`.

---

## 1. Контекст и «дух проекта»

CRM для **группы риелторов**. Кейс выбран не случайно: жена — риелтор, знает процессы изнутри,
поэтому домен «настоящий», а не выдуманный.

Продуктовая цель (важнее любых технических деталей):

> **Быстро получить хоть что-то, минимальную реакцию на запрос и прогресс — ценнее,
> чем дождаться полного ответа.**

Это мобильная история: риелтор на ходу, связь нестабильная, ему нужен мгновенный отклик
и постепенная подгрузка, а не «подумать 10 секунд и отдать всё сразу».

Отсюда принцип для бэкенда:

> **Оптимизируем «время до первого события», а не «время до полного ответа».**

Команда подтверждается почти сразу, а результат приходит **потоком тонких событий**
с прогрессом. Это и есть «дух» — и он же диктует архитектуру.

## 2. Три типа сообщений (и почему их нельзя смешивать)

Опыт показал: главная боль была в том, что запрос/ответ заставлял слать «всё одним куском».
Разделяем жёстко:

| Тип | Направление | Что это | Пример |
|---|---|---|---|
| **Команда** (intent) | фронт → источник | «сделай» | `doc.create {kind, data}` |
| **Факт/событие** | источник → все | «произошло» | `doc.person.created`, `file.uploaded` |
| **Запрос/снимок** | фронт → источник | «покажи текущее» | `docs(first, after)` |

- **События — единственный источник правды.**
- Команды — «намерения», без бизнес-правил на фронте.
- Запросы — снимки для первичного рендера (курсор, а не «весь результат одним куском»).

## 3. Карта системы

```
[ Browser: «тупой» UI ]  ──(WS /events, subscribe)──►  BFF (auth/session + WS-мост)
        │  ▲                                              │  (потоково форвардит события)
        ▼  │  команды                                     ▼
   [crm.commands]  ──►  ВЛАДЕЛЬЦЫ (источники)  ──►  [crm.events] (topic exchange)
                            │                                  │
                            │ doc:   Mongo (Doc + дискриминаторы) ├─► BFF → WS → фронт
                            │ files: GridFS                        ├─► search → Sphinx
                            │ (future)                             ├─► notify → Telegram
                            │                                      ├─► clickhouse (dual, проекция)
                            └── снимок: graphql (курсор)           └─► events-journal (аудит)
```

- **BFF — тупой адаптер**: аутентификация/сессия + HTTP↔AMQP + WS-мост. Ноль бизнес-логики.
- **Каждый сервис — источник правды** для своего агрегата и **единственное место решения**
  о форме, валидации и правилах. Поменял правило → пересобрал один сервис; фронт не трогал.

## 4. Сервисы и их события

| Сервис | Владеет | Эмитит | Потребляет |
|---|---|---|---|
| `doc` | Документы (Person/Property/Contract) | `doc.<kind>.created/updated/deleted` | `doc.create/update/delete` |
| `files` | GridFS | `file.uploaded`, `file.meta.updated`, `file.deleted` (эксперимент: `file.chunk`) | `file.upload/meta/delete` |
| `search` | Sphinx (проекция) | — | `doc.*` → `REPLACE` в rt-индекс |
| `notify` | Telegram | — | `user.notify` (дни рождения, события) |
| `graphql` | снимки (курсор) | — | запросы `docs(first, after)` |
| `clickhouse` | dual-проекция | — | `doc.*` → CH (ReplacingMergeTree) |

Важный выигрыш: **поиск становится проекцией** (слушает события), а не побочным эффектом
в запросном пути (раньше `Search.Add/Update` жил внутри middleware и требовал доступный Sphinx).

## 5. Контракты

**Команда** (идемпотентная):
```json
{ "commandId": "…", "type": "doc.create", "payload": { "kind": "person", "data": { … } } }
```

**Событие**:
```json
{ "eventId": "…", "type": "doc.person.created", "aggId": "…", "ts": 0, "actor": "…", "version": 1, "data": { … } }
```

**Обратная связь вместо статусов REST** — тоже события:
```json
{ "type": "command.confirmed", "commandId": "…", "aggId": "…" }
{ "type": "command.rejected",  "commandId": "…", "reason": "…" }
```

**Подписка** (WS): `subscribe { kinds: ["person","property"], aggIds: […] }` → BFF заводит
**пер-соединение очередь** и биндит её на `crm.events` по routing-ключу (RabbitMQ `binding_key`
с `*`/`#`). Фильтрация — на брокере; фронт ничего не решает.

---

## 6. «Тупой» фронт

Это не слабость, а цель. UI — **проекция событий**:
```js
store = {}                        // { aggId: {…} }
onEvent (e) { store[e.aggId] = e.data; render() }   // «экран = живой запрос к событиям»
```
- Никакого стейт-менеджмента и логики на фиче; экран = `v-for` по `store` с фильтром.
- Рендер «по одной записи» — естественно: пришло `created` → строка появилась, `updated` → обновилась.

## 7. Согласованность и компромиссы (честно)

- **Eventual consistency**: UI на мгновение может показать старое. Митигация: подтверждение
  команды + упорядочивание по `aggId` (`prefetch(1)` на консьюмере) + `version`-проверки.
- **Не полный event sourcing**: **снимок (Mongo) + дельта-события**. Replay целиком — тяжело и не нужно.
- **Межсервисных транзакций нет**; если нужна атомарность — сага/компенсация (для CRM обычно нет).
- **Идемпотентность**: at-least-once + дедуп по `eventId`/`commandId` (норм и честно).
- **Не событиевать каждый чих** — событие на осмысленный переход (`created/updated/deleted/uploaded`),
  а не на кейстрок.
- **Файлы в чанках**: образы в событиях гонять дорого (оверхед + память брокера). Правильно:
  писать в GridFS, эмитить `file.uploaded`, а байты отдавать по URL. Чанки (`file.chunk`) — как
  **экспериментальный срез**, чтобы показать, что поток реально сквозной.

## 8. Масштабирование / SaaS

Архитектура заточена под рост: **stateless-сервисы**, события для фан-аута, **курсор** вместо
«всего результата». **Мультитенантность уже заложена** полем `user` у каждого `Doc` — можно
партицировать по пользователю и масштабировать сервисы независимо. ClickHouse — проекция
событий для аналитики/больших объёмов.

## 9. История проекта (почему код такой, какой он есть)

Порядок разработки был: **бэк+фронт → минимальное отображение/редактирование → Telegram-бот →
RabbitMQ → GraphQL**. Каждый шаг — «подключить технологию, довести до MVP, разобраться со следующей».
Это заняло примерно полгода.

Поэтому в коде есть «странности»: незавершённый переход на GraphQL, инлайн-логика, отладочная
авторизация и т.п. — это **артефакты эволюции**, а не ошибки мышления. Сейчас проект в фазе
**консолидации** (монорепо, тесты, TS-миграция, событийно-ориентированная схема).

История — часть портфолио: интереснее показать **как думал** (почему сначала простые ручки,
потом AMQP, потом осознание «нужен поток, а не один ответ»), чем «идеальный» финал.

## 12. Переключаемый storage: Mongo ↔ ClickHouse

> Проверено на `@clickhouse/client@1.23.1` и локальном ClickHouse 26.9.7.9.

### JS-клиент ClickHouse (факты)

- Официальный клиент — **HTTP, не нативный**; два варианта: `@clickhouse/client` (Node, на
  **Node Stream API**) и `@clickhouse/client-web` (браузер/CF Workers, **Fetch + Web Streams**).
  TypeScript, zero deps. Нативного (TCP) JS-клиента от ClickHouse нет (нативно — Rust/Go/C++).
- **Потоковый по-настоящему** (не «pretend-async»): `resultSet.stream()` / `json()`.
- **Прогресс** (два пути):
  1. `JSONEachRowWithProgress` — в потоке идут `{ progress }`-строки (`RowOrProgress`, `isProgressRow`);
  2. `send_progress_in_http_headers` — сервер дописывает `X-ClickHouse-Progress`; в клиенте есть
     `max_response_headers_size` (иначе Node режет заголовки >16KB → `HPE_HEADER_OVERFLOW`).
- **Таймауты**: keep-alive (`idle_socket_ttl`, `eagerly_destroy_stale_sockets`), свой `http_agent`;
  тяжёлые запросы — серверные настройки через `clickhouse_settings`
  (`max_execution_time`, `send_timeout`, `receive_timeout`) + `query_id`.
- **`notify`/push как в pg (`LISTEN`/`NOTIFY`) — нет** (HTTP не умеет). Для пушей используем
  **RabbitMQ-события** (CH — проекция), прогресс — streamed.

### Адаптер `Storage`

Интерфейс: `saveDoc / getDoc / listDocs(kind, cursor) / search / deleteDoc / upsertFileMeta …`.
Реализации `MongoStorage`, `ClickHouseStorage`; выбор `STORAGE_BACKEND=mongo|clickhouse|dual`.
- **Dual**: пишем в оба, читаем из основного (Mongo); CH — аналитика/проекция; сверка по
  `version`/`mtime`, ретраи.

### Таблица CH (документный снимок)

```sql
CREATE TABLE docs (
  id String,
  kind LowCardinality(String),
  user String,
  version UInt64,
  ctime DateTime,
  mtime DateTime,
  data JSON
) ENGINE = ReplacingMergeTree(version)
ORDER BY (user, kind, id);
```

- **Upsert / последняя версия**: `LIMIT 1 BY id ORDER BY version DESC` (или `argMax`).
- **История — в event journal** (не в CH; CH — снимок) — снимает тревогу про «историю со схемой».
- **Индексы**: `JSON`-колонка гибкая, но произвольные вложенные пути не индексируются как в Mongo;
  для поиска **материализуем** поля (`lastName`, `firstName`, `address`, `price`) отдельными колонками
  + skip-индексы (`tokenbf_v1`/`ngrambf_v1`/`text`). Это осознанная цена «схема, если хотим индексы».

### Роль в событийной архитектуре

- CH — **проекция `crm.events`** (консьюмер), а не «второе хранилище в запросном пути»; переключатель
  меняет только источник снимков.
- Прогресс/быстрый отклик: `JSONEachRowWithProgress` + **курсор** (`WHERE id > last LIMIT n`).
